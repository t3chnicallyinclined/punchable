# The Rust port: workstream (2026-10-29)

The plan is `RUST.md`; this is the board. One row per ticket, in lanes that run in parallel because they touch
different crates. Status is edited here as tickets land; the gate for every ticket is `cd rust && cargo xtask gate`
plus the ticket's own proof. Nothing ships until T8 (the worker swap).

**Rules every lane follows**
- Popular crates, no hand-rolling (the owner's rule, 2026-10-29). Pin versions in `rust/Cargo.toml`
  `[workspace.dependencies]`; a crate says `{ workspace = true }`.
- A lane owns its crate directory and its generator under `rust/tools/`. It does not edit another lane's crate.
  `rust/Cargo.toml` and `Cargo.lock` are shared: add your lines, never reorder or remove others'.
- Edition 2024, `unsafe` forbidden, `thiserror` in libraries, `anyhow` in binaries, clippy pedantic clean, rustfmt 120,
  `//!` module docs that say what the module is for (not how), identifiers in backticks in docs.
- Proof against the Python it replaces: a CPython generator writes goldens from synthetic data (never real material)
  into `rust/crates/<crate>/tests/goldens/`; the Rust test compares as parsed JSON (`pk-kb/tests/goldens.rs` is the
  pattern). Property tests (`proptest`) where equality cannot hold.
- Nothing private in the public repo: no hostnames, no material, no other project's names. The commit guard runs.
- Edition 2024 traps met so far: `gen` is a reserved word (write `r#gen` or rename); `ndarray`'s `s!` macro expands
  with `#[allow(unsafe_code)]` and is refused under `unsafe_code = "forbid"` (index axes instead).
- A Python behaviour that the design said to relax is still ported exactly when it costs nothing (the gate's
  `str.isspace` set, the SDK's cache breakpoints): the allow-list is for things that cannot hold, not a licence.

## Deploying the images (T8 pk-worker, T9/T10 pk-api)

The images are never built on the production node. CI (`.github/workflows/rust.yml`, jobs `api-image` and
`worker-image`) builds both from the merge commit, checks the user, `docker save`s each to a gzip archive and keeps it
as a workflow artifact for 14 days (`punchable-api-rs-image-<sha>`, `punchable-worker-rs-image-<sha>`); the job log
prints the image id and the archive's sha256. The deploy path, written without host names (the private runbook has them):

1. `gh run download <run-id> -n punchable-api-rs-image-<sha>` (and the worker's), then check the archive's sha256
   against the job log.
2. `gunzip -c punchable-api-rs.tar.gz | docker load` on a machine with Docker; the loaded image id equals the
   `image id:` line in the job log.
3. Tag it for the cluster registry, push, and read the pushed digest:
   `docker tag punchable-api-rs:ci <registry>/punchable-api-rs:<sha>`, `docker push <registry>/punchable-api-rs:<sha>`,
   `docker inspect --format '{{index .RepoDigests 0}}' <registry>/punchable-api-rs:<sha>`.
4. Roll out by that digest, never a tag: render the manifest with the digest
   (`bash infra/render.sh infra/k8s/prepared/t10-api-rs.yaml "" <registry>/punchable-api-rs@sha256:<digest>`, or
   `PK_IMAGE_REF_RS=...`) and apply the output with the cluster tooling. `infra/render.sh <file> [image_ref
   [image_ref_rs]]` refuses a manifest with any `__NAME__` placeholder left, so a pk-api manifest cannot ship
   `__IMAGE_REF_RS__`. The ServiceMonitor in that file is rendered only with `PK_SERVICEMONITOR=1` (the cluster needs
   the Prometheus Operator CRD). The worker swap rendered the Rust worker manifest (now `infra/k8s/35-worker.yaml`, LIVE 2026-11-07; the Python
   one kept at `infra/worker/python/35-worker.yaml` for rollback) with the worker image's digest as `image_ref`.
5. The worker's API base URL is one setting: `PK_WORKER_API` in `infra/config.env` fills `__PK_WORKER_API__` in both
   worker manifests (default `http://punchable-api`, the Python Service). The cutover sets
   `PK_WORKER_API=http://punchable-api-rs` and re-renders the worker; the NetworkPolicies in the prepared file already
   admit the worker to pk-api (ingress on pk-api, egress on the worker). Rollback is the same variable unset.

## Working in parallel

One agent per lane, each with its crate directory and its generator, none editing another's; the lead merges,
runs the gate and commits. When two lanes need the same new workspace dependency, both add the same line; the lead
keeps one. `cargo build -p <crate>` and `cargo test -p <crate>` are the per-lane commands; `cargo xtask gate` is the
lead's.
